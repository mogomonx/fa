# FA Records — Architecture

Website that ranks a WCA group's official stats (single and average, every WCA event). It started as a replacement for a manually updated Google Sheet for the FA group and has grown into a site where anyone can build the same thing for their own group, logged in or as a guest, plus a private personal profile page for every logged-in WCA user, plus (session 10) automatically built **state rankings** for Australia. Long-term goal: grow into a full WCA rankings site (country/state rankings, custom user-made lists, this group view as one feature), built up from what exists, not rewritten.

- Repo: `github.com/mogomonx/fa`
- Hosting: GitHub Pages, served from `docs/` (`https://mogomonx.github.io/fa`)
- Data: **every list is a database list.** The list definitions (name, visibility, kind, members) live in Supabase Postgres. A GitHub Actions workflow builds each list's JSON and uploads it to a **private Supabase Storage bucket** (`list-data`). Nothing list-related is committed to the repo.
- Backend: Supabase free tier. Postgres + auth + Storage + one Edge Function. Holds accounts, list definitions, build status, opt-outs, guest edit-token hashes, display-name settings, region overrides, admins, and the built JSON.
- Budget: **none**. Nothing that needs a paid plan (GitHub or Supabase) can be part of the design. The owner would rather people can create groups at all than have every privacy guarantee.

**Status (read this first, updated 2026-10-27):** the site is **published** (owner announced it 2026-10-27; users are asked to report bugs to the owner). Everything planned for the custom-lists project, the "smaller fixes" sessions 0 to 10, state rankings (10a to 10c), the Parquet pipeline and instant lists (sessions 11 to 18) and the pre-release security review (session 19) is built; the per-session table is in section 9. FA is an ordinary database list (slug `fa`, **private**, permanent). Open work: state profiles should say "<state> rank" instead of "group rank", the small-fixes queue, the owner's dashboard checks and housekeeping (all in section 9), and the remaining loading-speed work before any WCA-wide data (section 9, "Loading speed"; Victoria's slow load was found and fixed on 2026-10-27). The owner is also rewriting the visual side of the HTML pages by hand (section 11). **2026-10-28:** four new Misc statistics (Podiums & Wins, Sub-X Clubs, Attendance, Kinch What-If) live in `tabs/more-stats.js`. **2026-10-30 (session 22, plan items E1 to E5):** searchable person pickers (`js/person-picker.js`) and Head-to-Head clear buttons, tables that fit the width, Record Age and Historical Records toggles, 12 colour presets in a grid plus a font picker with self-hosted fonts (`docs/fonts/`), and the Sub-X Clubs rework (first people to get under a time).

## 1. Data flow

```
Supabase tables lists + list_members + profiles (+ preferred_name_lists, person_regions)
        │  scripts/sync-lists.js   (service key; writes build/ — git-ignored, never committed;
        │                           resolves each member's displayName, see section 4 "Display names";
        │                           also reports STATE lists separately and writes build/states-input.json)
        ▼
   update-custom-lists.yml  (started on demand by Supabase trigger_build() via pg_net → workflow_dispatch, mode pending; also every 15 min / daily / weekly / manual)
        │  scripts/extract-bests-from-parquet.py  (since step 7: personal bests + official ranks + countryIso2 for ALL regular lists from persons / ranks_* Parquet → results.json)
        │                                          fallback scripts/fetch.js (WCA API, each distinct person once), only if the Parquet route fails or isn't available
        │  build scripts, run with LISTS_ROOT=build  → build/data/<slug>/*.json
        │  scripts/convert-to-parquet.py  (daily + weekly: export TSVs → Parquet in build/parquet, uploaded to Cloudflare R2 with parquet-meta.json)
        │  scripts/extract-from-parquet.py  (ONE call for all lists: full-results.json from the Parquet files, local or the public R2 URL;
        │                                    fallback scripts/parse-export.js streams the 350MB export once)
        │  scripts/extract-state-source.py  (state lists, Parquet route: persons/competitions/results/ranks → build/states-source.json)
        │  scripts/build-states.js  (state lists: assigns people to regions from build/states-source.json (Parquet) or the export (fallback), writes results.json
        │                            + state-assignments.json + state-unassigned.json per state; the usual build-rankings etc. then run on each state slug)
        │  scripts/fetch-upcoming.js (its own workflow update-upcoming.yml, daily + started for brand-new lists: ONE shared scan of upcoming competitions for all lists)
        │  scripts/upload-lists.js → Supabase Storage bucket `list-data`, path <list uuid>/<file>.json
        │  scripts/mark-lists.js   → lists.data_level / built_at (via mark_list_built())
        ▼
   main.js: get_list_by_slug(slug) → Storage download (policy decides who can read)

Accounts (separate path):
Browser ──► WCA /oauth/authorize ──► Supabase Edge Function `wca-auth` ──► auth-callback.html ──► Supabase session
Browser ──► Supabase (publishable key, row level security) ──► profiles / lists / list_members / list_opt_outs
            (used by lists.html via js/lists-page.js to create, edit, delete, browse and leave lists;
             by js/profile-button.js (home.html card) and js/name-settings.js for the personal profile and display-name settings;
             by js/states-page.js for the "Your state" block: region RPCs + state-assignments.json;
             by js/admin-page.js + admin-person.js (admins only): admin_* RPCs, direct list edits/deletes, state-assignments.json + state-unassigned.json)

Guests (not logged in): Browser ──► Supabase RPCs create/get/update/delete_guest_list (edit token in the call)
            token kept in localStorage; claim_guest_list() moves the list onto the account at login

Parquet (public WCA data only): Browser ──► js/db.js (DuckDB-WASM, loaded on demand; used by `instant-rankings.js` for lists with no built data, and by `member-search.js` for the list editor's name search) ──► R2 public URL
            persons / ranks_single / ranks_average / competitions / round_types / results .parquet

Site settings (no backend): settings.html ──► localStorage (colours, On This Date, Time frame)
            ──► every page reads them on load (theme.js for colours; timetravel/index.js on rankings pages, not on state lists)
```

Guest lists and personal profile lists are built exactly like any other list: `sync-lists.js` doesn't special-case owners. **State lists are the exception**: they have no members in `list_members` and are built from the export by `build-states.js` (see "State lists" below).

### Data sources
| Source | Used for | Notes |
|---|---|---|
| WCA v0 API `/persons/:id` | Profile picture (home page "My profile" card); personal bests, ranks, official name and country only through `fetch.js`, which since step 7 is the fallback for the Parquet route | No way to list a person's competitions. **Rate limited (HTTP 429)**: see `fetch.js` below |
| WCA Results Export (~350MB TSV, v2 format) | Full result history, attempts, placements, round names; also everyone's official PBs and ranks (state lists; since step 7 also the personal bests of ordinary lists) | Downloaded once per workflow run, read once for all lists. **File names carry a `WCA_export_` prefix** (e.g. `WCA_export_persons.tsv`); `parse-export.js` and `build-states.js` accept the prefix or none. Files used: `results.tsv`, `result_attempts.tsv`, `competitions.tsv`, `round_types.tsv` (official round names and order), and for state lists also `persons.tsv`, `ranks_single.tsv`, `ranks_average.tsv`, `countries.tsv` (id/name → iso2; used by `build-states.js` and, since step 7, by `convert-to-parquet.py` for `persons.parquet.country_iso2`) |
| WCA OAuth (`/oauth/authorize`, `/oauth/token`, `/api/v0/me`) | Login: WCA user id, name, WCA ID | Scope `public` only |
| WCA competitions list `/api/v0/competitions?start=&end=&page=` | The set of competitions in the next ~182 days (name, dates, city, country, event ids, registration open time) | Used by `fetch-upcoming.js` |
| Public WCIF `/competitions/:id/wcif/public` | Registrants (accepted only) with their registered events | Used by `fetch-upcoming.js`. A 404 (no public WCIF) is skipped |

`competitions.tsv` header (confirmed by the owner): `id, name, information, external_website, venue, city_name, country_id, venue_address, venue_details, cell_name, cancelled, event_specs, delegates, organizers, year, month, day, end_year, end_month, end_day, latitude_microdegrees, longitude_microdegrees`. For Australian competitions `city_name` is consistently "City, State" (the owner reports it maps very consistently). Coordinates are available if a coordinate-based fallback is ever needed.

### Workflows (`.github/workflows/`)
| Workflow | Cadence | Purpose |
|---|---|---|
| `update-custom-lists.yml` | On demand (database trigger, mode `pending`), every 15 min (`pending`), daily 06:30 UTC (`bests`), weekly Sunday 07:00 UTC (`full`), or manual with a `mode` input | Builds database lists and state lists and uploads the JSON to Storage; also pings Supabase (keep-alive for the free project); since session 11 also converts the export to Parquet and uploads it to Cloudflare R2 (daily + weekly); the weekly run starts with the list cleanup (session 15) |
| `update-upcoming.yml` | Daily 07:30 UTC, manual, or started by `update-custom-lists.yml` when a brand-new list is built | Shared worldwide scan of upcoming competitions for every regular list; uploads `upcoming.json` (session 13). Own concurrency group |
| `keep-alive.yml` | Daily 05:17 UTC, or manual | Makes an empty commit when the last commit is 30+ days old, so GitHub doesn't disable scheduled workflows after 60 days of inactivity |

GitHub also runs its own `pages-build-deployment` after each push; that is automatic and expected in the Actions list.

`update-custom-lists.yml` details:
- Repository secrets required: `SUPABASE_URL` (bare project URL) and `SUPABASE_SERVICE_KEY` (the secret/service key). Plain **repository** secrets; the job declares no `environment:`.
- Since session 11 also required for the Parquet upload: `R2_ENDPOINT_URL`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` (repository secrets). The workflow file also contains the bucket's public URL (`R2_PUBLIC_URL` in the Full build step's env); it is public by design.
- Permissions are `contents: read` — it cannot commit. `concurrency: custom-lists` (no cancel) so runs queue.
- Env `LISTS_ROOT=build` (see section 2).
- Step outputs from the sync step: `slugs`, `new_slugs` (regular lists), `state_slugs`, `state_countries` (state lists).
- **Pending** mode: `sync-lists.js --pending` selects lists where `built_at` is null or older than `dirty_at`. Since step 7 (session 17) there is **no separate basic build**: every pending list, brand-new ones included, goes straight through the **full build** (below) and is uploaded and marked `full`; while a new list (`data_level = 'none'`) waits, the browser shows instant rankings (section 4). **Pending mode never skips dormant lists** (section 6, "List lifecycle") and does not scan for Upcoming itself: when it builds a brand-new list it starts `update-upcoming.yml` (below), and the daily run covers anything missed.
- **Bests** mode (daily): `sync-lists.js --built`, then (since session 11) downloads the export, converts it to Parquet and uploads it to R2 (about a minute, `continue-on-error`), so the R2 copy is at most a day old. **Since step 7** the "Daily personal bests" step comes after that: it runs `extract-bests-from-parquet.py <all slugs>` on the fresh local `build/parquet` (if the conversion succeeded), uses `fetch.js` instead if the conversion didn't succeed or the extractor fails, then `build-rankings.js` per list and re-uploads `rankings.json` only. Its condition starts with `!cancelled()`, so a failed export download doesn't stop the daily rankings refresh (it then uses the WCA API). (Upcoming is no longer part of this workflow.) **State lists are not touched in bests mode, and neither are dormant lists (session 15).**
- **Full** mode (weekly): first the **cleanup step** (`scripts/cleanup-lists.js`, `continue-on-error`, session 15: deletes expired lists and sweeps orphaned Storage folders; section 6, "List lifecycle"), then `sync-lists.js --all` (which skips dormant lists), export download, Parquet conversion and R2 upload, then the full build of everything including every state list (using the fresh local Parquet files). (Upcoming is no longer part of this workflow.)
- **Work out export URL / Download WCA results export** steps run only when the mode is not `pending` (daily and weekly runs, to make the Parquet files). A `pending` run (ordinary lists and state lists) never downloads the export up front: it reads the public R2 copy, and the Full build step's `ensure_export` function downloads the export only if the Parquet route fails (session 12). The URL step tries `scripts/get-export-url.js` (sends a `User-Agent`; WCA blocks requests without one), then `curl` with the same header; the download step refuses to run `curl` on an empty URL.
- **Full build order (one step, "Full build (regular lists and state lists)", since session 11):** (1) if there are regular lists (since step 7): `extract-bests-from-parquet.py $SLUGS` from `PARQUET_SRC` (worked out just before, see below), or `fetch.js $SLUGS` once if there is no Parquet source or the extractor fails, then `build-rankings.js` per list; (2) `PARQUET_SRC` is worked out first (full mode: local `build/parquet` if the conversion succeeded; pending mode: the public R2 URL; `pip install duckdb` when set). If there are state lists: `extract-state-source.py $STATE_COUNTRIES` then `build-states.js parquet $STATE_COUNTRIES`; if either fails, or there is no Parquet source, `ensure_export` then `build-states.js /tmp/wca-export $STATE_COUNTRIES` (the old TSV route); then `build-rankings.js` per state slug; (3) `full-results.json` for ALL slugs in one call: `extract-from-parquet.py` reading the fresh local `build/parquet` (full mode) or the public R2 URL (pending mode), and **if that fails or isn't possible, `parse-export.js /tmp/wca-export $SLUGS $STATE_SLUGS`** (downloading the export first if it isn't there); (4) regular lists: the five history scripts per list; state lists: only `build-individual-rankings.js` and `build-historical-records.js`, four at a time (`xargs -P 4`); (5) `upload-lists.js --level=full` and `mark-lists.js --level=full` for regular and state slugs together.
- **State rankings:** no longer a separate step (merged into the Full build step above). State lists get real `full-results.json`, `individual-rankings.json` and `historical-records.json`; `streaks.json`, `recent-activity.json` and `rolling-averages.json` are deliberately not built for them (the first version that built all five took about 7.5 minutes; skipping them takes about 1).
- **Upcoming scan (session 13): its own workflow, `update-upcoming.yml`.** Daily 07:30 UTC, manual, and started by `update-custom-lists.yml` (step "Start the Upcoming scan for brand-new lists", `gh workflow run`, needs `permissions: actions: write`, `continue-on-error`) when a `pending` run builds a brand-new list. Its own `concurrency` group (`upcoming-scan`, no cancel; GitHub keeps only the newest waiting run), so the roughly 9-minute scan can no longer hold up a list build. Steps: checkout, Node, `sync-lists.js --all` (regular lists only are used: its `slugs` output), then `node scripts/fetch-upcoming.js $SLUGS` and `node scripts/upload-lists.js --files=upcoming.json $SLUGS`. No `continue-on-error`: a failed scan shows as a red run (the previous `upcoming.json` stays in Storage).
- `mark_list_built(..., 'full')` only applies if `dirty_at` is unchanged since the build read the list, so an edit made mid-build leaves the list pending and it gets rebuilt next run.
- Regular lists with no members are skipped.
- Uploads and REST calls retry on network errors, 429 and 5xx (5 attempts, waits of 3, 6, 12, 24 seconds); errors are trimmed to one line.
- GitHub's scheduled runs are late (the `*/15` cron ran about every 2 hours when measured), so since session 12 the schedule is only a fallback for on-demand builds ("On-demand builds" below). For testing, use the manual **Run workflow** button (mode `pending`; `bests` to refresh Upcoming and rankings; `full` to repair data after a bad run or after an event-definition change).
- **`fetch.js` behaviour (important; since step 7 only the last-resort fallback for personal bests, used when the Parquet route is unavailable or fails):** takes every list slug at once and fetches each *distinct* person once, however many lists they are on. Results are cached in `build/person-api-cache.json` for the rest of the run (the build folder is wiped at the start of every run by `sync-lists.js`, so the cache never goes stale). WCA 429/5xx/network errors are retried up to 8 times (waits honour `Retry-After`, otherwise 5s doubling to 60s; 400ms pause between people). A person who really doesn't exist (404) is built empty with `error: 'Not found on the WCA site'` and does not block anything. **If anyone still can't be fetched after the retries, the step exits 1 and nothing is written or uploaded**; affected lists stay pending and the next run retries.
- **`extract-bests-from-parquet.py` (step 7, session 17):** `python scripts/extract-bests-from-parquet.py <slug...>` writes `<LISTS_ROOT>/data/<slug>/results.json` for REGULAR lists in exactly the shape `fetch.js` writes (`fetchedAt`, `people[]` with `wcaId`, `name`, `countryIso2` and `events`, which holds `single`, `average`, `singleRanks`, `averageRanks` for every event id, null when missing). Reads `persons.parquet` (official name, `country_iso2`), `ranks_single.parquet` and `ranks_average.parquet` from `PARQUET_DIR` (a local folder or the public R2 URL; members from `build/lists/<slug>.json`; the event list comes from `scripts/lib/events.js` through `node -e`). Name = the member's `displayName`, else the official name, else the WCA ID. A person missing from `persons.parquet` gets `error: 'Not found on the WCA site'`, as in `fetch.js`. `fetchedAt` is the Parquet copy's `parquet-meta.json` `generatedAt`, so `rankings.json` `dataFetchedAt` now means "as of the Parquet copy", not an API call. **Official ranks come from the export, so they can be up to a day behind the live API** (accepted; a manual `full` run refreshes them). Staleness guard as in the other extractors: a remote copy older than `PARQUET_MAX_AGE_DAYS` (default 3) exits 1 and the workflow falls back to `fetch.js`; it also exits 1, writing nothing, if no one is found or no rank rows match. If `persons.parquet` has no `country_iso2` column yet (an old R2 copy) it warns and writes null countries (no flags) until the next daily/weekly refresh. It does NOT handle state lists (`build-states.js` writes theirs). The helper code (event ids, freshness check, DuckDB setup) is copied from `extract-from-parquet.py`, not shared; cleanup later.
- **`parse-export.js` behaviour:** `node scripts/parse-export.js <export-dir> [slug ...]`. One pass over `results.tsv` and `result_attempts.tsv` serves all lists: each person's results are read once and written into every list they are on (with that list's own displayName). With one slug or none it behaves as it always did.
- **`fetch-upcoming.js` behaviour:** `node scripts/fetch-upcoming.js <slug ...>`. **Worldwide scan, no country filter.** Pages through every competition starting in the next 182 days, then fetches each one's public WCIF **once** and matches registrants (accepted only) against the members of **all eligible lists** at the same time. Competitions whose `registration_open` is still in the future are skipped (nobody can be registered). 250ms pause between requests; 429/5xx/network errors are retried up to 8 times (honours `Retry-After`, otherwise 5s doubling to 60s); a 404 on a WCIF is skipped. **If any competition still fails after the retries, nothing is written and the step exits 1** (the previous `upcoming.json` in Storage stays). Lists with more than **`MAX_MEMBERS` = 50** members are not matched; they get `{skipped: true, maxMembers: 50}` instead. Expect roughly a thousand requests, about 5 to 10 minutes per run. Attendee names use the list's resolved displayName.
- Timings (current): a `pending` run for one new list is about 40 to 55 seconds of job time (about 5 seconds is runner setup; the merged single build since step 7 has not been re-timed). The weekly `full` run took 5m22s (2026-10-22). `full-results.json` for 17 lists from Parquet takes about 9 seconds. The Upcoming scan (about 9 minutes) has its own workflow. Because of `concurrency: custom-lists`, a list created while the daily or weekly run is busy waits behind it. The floor for the GitHub Actions route is roughly 30 to 50 seconds; anything faster is the browser-side route (instant lists, section 4).

### On-demand builds (session 12, 2026-10-20)
- **What:** instead of waiting for GitHub's `*/15` cron (measured about every 2 hours), the database starts the workflow itself. Postgres function `trigger_build()` (security definer) calls GitHub's `workflow_dispatch` on `update-custom-lists.yml` (ref `main`, mode `pending`) through `pg_net`, with the token read from the Supabase Vault secret `gh_workflow_token` (fine-grained GitHub token, repo `fa` only, Actions read/write).
- **Triggers on `lists`** (statement level): `build_on_list_insert`, and `build_on_list_update`, which fires only when some list's `dirty_at` changed (so `mark_list_built` does not loop). A new list normally causes two dispatches (the list insert, then the member insert); the second finishes fast.
- **Token expiry:** when the token expires, on-demand builds stop silently and the 15-minute schedule is the only fallback. **The token expires on 18 January 2027**: make a new one (and replace the Vault secret) before then.
- **Debugging:** `select status_code, content from net._http_response order by created desc limit 5;` (204 = success).
- **Files:** the SQL lives only in `supabase/schema.sql` (there is no separate `007_build_trigger.sql` file); the `vault.create_secret` line is NOT in the repo.
- **Workflow change that goes with it:** the export steps no longer run in `pending` mode; state lists build from Parquet too (see "Full build order").
- **Limits:** the dispatch-to-start delay is not measured; instant lists (section 4) cover the wait.

### State lists (session 10a)
- **What they are:** one list per region (`kind = 'state'`, `country` + `region`, slug `state-<cc>-<region>`, e.g. `state-au-nsw`), no owner, `visibility = 'unlisted'` (reachable at `index.html?list=state-au-nsw`, never shown on `lists.html`, not enumerable). Currently eight Australian lists (NSW, VIC, QLD, WA, SA, TAS, ACT, NT), seeded by SQL. They are public data, so unlisted/readable-by-slug is fine. They reuse the whole rankings page: the build writes the same files as a "basic" build (real `rankings.json`; since session 11 also real `full-results.json`, `individual-rankings.json` and `historical-records.json`, but still no streaks / recent-activity / rolling files) with `data_level` / `meta.json` level `full` so the "history still being processed" note doesn't show. Since 10b the rankings page runs them in **state mode** (section 4).
- **Sync:** `sync-lists.js` separates `kind = 'state'` rows. `--pending`: every state list of a country is chosen when any of that country's state lists is pending (`built_at` null or older than `dirty_at`). `--all`: all state lists. `--built` (daily): none. It writes them into `lists-manifest.json` and `state.json` (so `getListContext`, `upload-lists.js` and `mark-lists.js` work unchanged) and writes **`build/states-input.json`**: `{lists:[{slug,country,region}], overrides:[person_regions rows], names:{wcaId: preferredName for visibility 'everywhere'}}`. Overrides are read with paging (`restAll`, 1000 per page).
- **`build-states.js`:** `node scripts/build-states.js <export-dir | parquet> <country> [country ...]`. **Two sources (11b):** `parquet` reads `build/states-source.json` (written by `scripts/extract-state-source.py`); an export folder is the old TSV path, kept as the fallback. The rest of this bullet describes the TSV path; the Parquet path feeds the same logic from the `persons`, `competitions`, `results` and `ranks_*` Parquet files. Reads `persons.tsv` (current row only, `sub_id` 1; keeps people of the requested countries plus override people), `competitions.tsv` (region parsed from `city_name`, see below), one pass over `results.tsv` for which mapped competitions each person attended, then `ranks_single/ranks_average` for PBs and NR/CR/WR. Writes `build/data/<slug>/results.json` per state list in exactly the shape `fetch.js` writes. It also writes **`state-assignments.json`** into every state list's folder: `{generatedAt, country, auto: {wcaId: region}}`, each person's DETECTED region ignoring overrides (people who chose to be hidden are left out, and so are people with no detected region). It also writes **`state-unassigned.json`** into every state list's folder: `{generatedAt, country, people: [{wcaId, name, country, regions: {REGION: competitions}}]}`, the people of a built country who have competed in mapped competitions but whose region never reached the minimum (for the admin view; people with an override, or who chose to be hidden, are not in it). **Any missing file or column stops it with the real header printed; nothing is then published.** It also stops if it finds no people, no mappable competitions, or ends with nobody in any list. The log prints: competitions mapped vs unmapped (first 40 unmapped names), how many people were assigned by override / auto (recent) / auto (all time), who was left out, and people per state.
- **Region of a competition:** from `city_name`: last comma-part that is a state name or abbreviation, then a trailing token ("Perth WA"), then a major-city fallback (Sydney, Melbourne, Brisbane, Perth, Adelaide, Hobart, Canberra, Darwin and a few others). To add a country, add an entry to `COUNTRIES` in `build-states.js` and extend `valid_region()` in SQL.
- **Who is in a state list (in order):** (1) an override row (`person_regions`) — `hidden` = left out, otherwise that region, for anyone of any WCA country; (2) otherwise people whose WCA country is a built country get the region with the most distinct **competitions** (not rounds) in the **last 3 years**, falling back to **all time**, requiring **at least 2** competitions in the region; ties go to the region of the most recent competition; (3) nobody else. People with no official result at all are left out. Names: the person's preferred name when `name_visibility = 'everywhere'`, else the official WCA name (owner-typed names and `official_names_only` don't exist for state lists).
- **Kinch / Sum of Ranks** are relative to the **state's own best** (existing `build-rankings.js` logic over the state's people). NR/CR/WR in the records table come from the export's ranks tables.
- **What state lists have and lack (updated session 11):** they have `rankings.json`, `full-results.json`, `individual-rankings.json` (each event's ranked list capped at 2,500 entries) and `historical-records.json`. Since session 13 they also get `streaks.json` (`build-streaks.js` in the state history step; people with no results are left out, and `byEvent` lists only people with a result in that event and type) and `upcoming.json` (`kind: 'state'`: the competitions held in the state, no registrations; built by `fetch-state-upcoming.js` inside `update-upcoming.yml`). They have NO `rolling-averages.json` or `recent-activity.json`, and On This Date / Time frame are skipped for them (`main.js`). The rankings page hides only the parts that depend on the missing files (section 4, "State mode"). Sizes are large: VIC is about 62MB across its files (28.7MB `full-results.json`, 24.6MB `individual-rankings.json`), which loads slowly; the long-term fix is the browser-side Parquet route (section 9).
- **Rebuild trigger:** any region change (set/hide/clear, by the person or an admin) calls `mark_state_lists_dirty(country)`, which bumps `dirty_at` on that country's state lists; since session 12 that fires an on-demand `pending` build (and the 15-minute schedule is the fallback), which builds from Parquet and only downloads the export if that fails. To force one by hand: `update lists set dirty_at = now() where kind = 'state';` then run mode `pending`. A name change made by an admin (`admin_set_name` / `admin_clear_name`) calls `mark_person_dirty`, which bumps every state list and every list the person is on.


### Parquet pipeline (session 11, 2026-10-19)
Goal: make list builds faster and prepare for a bigger (WCA-wide) site without leaving the free tiers. The export is converted once a day into small columnar files; builds query those instead of streaming the 350MB TSVs.
- **Where:** Cloudflare R2 bucket `wca-parquet-data` (free tier: 10GB storage, about 1M writes and 10M reads per month, no egress fees; the files total about 180MB). Public read through the bucket's r2.dev URL (`https://pub-968764766d9f40a8b51a059fe21a1a34.r2.dev`). **Public data only: nothing private may ever go in this bucket.** CORS rule on the bucket: origin `https://mogomonx.github.io`, methods GET and HEAD, header `Range`, exposed headers `Content-Length, Content-Range, ETag, Accept-Ranges` (checked from the live site: a ranged fetch returns 206). Writes come from the workflow with `aws s3 sync` (secrets in section 1, workflow details).
- **Files** (`build/parquet/` → bucket root; ZSTD; 100,000-row row groups, except `persons` at 10,000 and the person-sorted `ranks_*` at 20,000 since step 8):

| File | Contents |
|---|---|
| `persons.parquet` | `wca_id, name, country_id, gender, country_iso2` (current row only; `country_iso2` added in step 7 from `countries.tsv`, matched on the country id or name, falling back to a two-letter `country_id`; 0 of 300,834 persons had none on the first run). **Sorted by `wca_id`, 10,000-row row groups** (step 8) |
| `ranks_single.parquet`, `ranks_average.parquet` | `wca_id, event_id, best, world_rank, continent_rank, country_rank`, **sorted by `wca_id` then event, 20,000-row row groups** (step 8; for lookups by person) |
| `ranks_single_by_event.parquet`, `ranks_average_by_event.parquet` | the same rows sorted by event then world rank, 100,000-row row groups (step 8; nothing reads them yet, kept for the later world / country rankings pages) |
| `competitions.parquet` | `id, name, city_name, country_id, year, month, day, end_year, end_month, end_day` |
| `round_types.parquet` | `id, rank, name, cell_name` |
| `results.parquet` | `result_id, wca_id, person_name, event_id, competition_id, round_type_id, pos, best, average, attempts, year, month, day` (about 7M rows, about 166MB). `attempts` is a `BIGINT[]` in attempt order and includes rounds with more than 5 attempts (some 2026 rounds have 8 to 28). **Sorted by person** (then event, date) so one person's or one list's rows sit in few row groups |
| `parquet-meta.json` | `{generatedAt, scriptVersion}` freshness stamp (not Parquet) |

- **`scripts/convert-to-parquet.py`** (v8.4; v8.4 = the step 8 sorting above, each ranks file read once and written twice, and a check that both copies have the same row count; the rest as in v8.3): reads every column BY NAME (the persons header is `name, gender, wca_id, sub_id, country_id`, so positional lookups were wrong), never lets DuckDB sniff the dialect (`auto_detect=False`, the column list is built from the real header), reads `competitions.tsv` with Python's `csv` module and `QUOTE_NONE` (names contain stray quotes), uses a file-backed DuckDB database with a memory limit of about 70% of the runner's RAM (an in-memory version ran out of memory), aggregates attempts as five pivot columns plus a small side table for attempt numbers above 5, stops with the real header printed if a column is missing, and checks every output has rows. About 50 seconds.
- **`scripts/extract-from-parquet.py <slug...>`**: writes `<LISTS_ROOT>/data/<slug>/full-results.json` for all given lists in one query, in the same shape as `parse-export.js` (`wcaId, name, eventId, competitionId, competitionName, date, round, roundName, roundRank, pos, single, average, attempts`). Members come from `build/lists/<slug>.json` (regular lists) or `build/data/<slug>/results.json` (state lists); the event list comes from `scripts/lib/events.js` through `node -e`, so FTO and `SINGLE_ONLY_EVENTS` stay in one place. `PARQUET_DIR` is a local folder (default `build/parquet`), an `https://` URL (the public R2 URL, via DuckDB `httpfs`, no credentials) or `s3://` (needs the R2 credentials in env; untested). `--out-dir` writes elsewhere. **Staleness guard:** for an `https://` source it reads `parquet-meta.json` and exits (so the workflow falls back to `parse-export.js`) if the copy is older than `PARQUET_MAX_AGE_DAYS` (default 3); a missing stamp only warns (expected until the first daily/weekly run after v8.3).
- **`scripts/extract-state-source.py <country...>`** (session 12 / 11b): queries the `persons`, `competitions`, `results` and `ranks_*` Parquet files (local folder or the public R2 URL, through `PARQUET_DIR`) and writes `build/states-source.json` for `build-states.js parquet`. Same staleness guard as `extract-from-parquet.py` (exits 1 if the R2 copy is older than 3 days, so the workflow falls back to the export). It has an `ALIASES` map (AU: `australia`, `au`) that must be extended together with `COUNTRIES` in `build-states.js` when a country is added.
- **`scripts/compare-full-results.py <dirA> <dirB> <slug...>`**: test tool; compares two folders of `full-results.json` entry by entry (key person + competition + event + round). Result of the 2026-10-19 shadow test: all 17 lists identical to `parse-export.js` except attempts beyond the fifth, which led to the side table above.
- **How the workflow uses it** (details in the workflow bullets above): `bests` and `full` runs download the export, convert and upload (`continue-on-error`); `full` builds from the fresh local files; `pending` builds from the public R2 copy (at most about a day old); any failure falls back to `parse-export.js`.
- **Not on Parquet yet:** `fetch-upcoming.js` (personal bests moved to Parquet in step 7; `fetch.js` stays as the fallback), and every browser tab except the instant-rankings path (section 4, "Instant rankings"). (`build-states.js` moved onto Parquet in session 12 / 11b, with the export as fallback.)
- **Browser side:** `docs/js/db.js` loads DuckDB-WASM (jsDelivr, pinned 1.28.0) on first use and exposes `queryParquet(sql)`, rewriting `FROM results.parquet` / `JOIN competitions.parquet` to a full address. **Since step 8 only `instant-rankings.js` and `member-search.js` use it (`parquet-test.js` was deleted), and it must only be loaded with a dynamic `import()` inside a try/catch**: an earlier static import in `main.js` made every rankings page fetch DuckDB from a CDN and would have broken pages if the CDN failed (removed 2026-10-19). **Worker (sessions 14 and 15):** a Cloudflare Worker `wca-parquet` serves the bucket through an R2 binding (`BUCKET`), passes `Range` requests through and adds CORS for the site; its address is `https://wca-parquet.fawcastats.workers.dev` (the account's workers.dev subdomain was changed from the default to `fawcastats` on 2026-10-22). Since session 15 `db.js` uses it first: on the first query of a page session it fetches `parquet-meta.json` from the Worker with a 3-second timeout and uses the Worker if that works, otherwise `r2.dev` (any network error, timeout, 429 when the free 100,000-requests-a-day limit is used up, or 5xx; Cloudflare's over-limit page has no CORS headers, so it shows up as a network error). A query that fails part-way through via the Worker with a network/HTTP-looking error is retried once on `r2.dev` (and the session stays there); 404s and SQL mistakes are not retried. `db.js` also turns BigInt results into numbers. `getParquetBase()` shows which address is in use (for the console). Builds in GitHub Actions keep reading `r2.dev` (`R2_PUBLIC_URL` in the workflow). The Worker script is edited in the Cloudflare dashboard (Workers & Pages > `wca-parquet` > Edit code); since session 16 a reference copy is in the repo at `cloudflare/wca-parquet-worker.js` (not deployed from there; paste changes into the dashboard). The reference copy adds a `Timing-Allow-Origin` header so the browser can report transfer sizes (confirm it was pasted into the dashboard). **Never send thousands of literal IDs in an `IN (...)` list through `queryParquet`**: it crashed DuckDB-WASM ("memory access out of bounds") at about 12,000 IDs; load the IDs into a temp table (`CREATE OR REPLACE TEMP TABLE ...`, `INSERT ... VALUES` in chunks of 500) and use `IN (SELECT ...)`. After a WASM crash the page must be reloaded. **Lookups by person (step 8):** look people up with one exact `WHERE wca_id = '...'` per person (`UNION ALL`, up to 200 people; a temp table above that) and `SET enable_object_cache = true`. A literal `IN (...)` list did not skip row groups (26.8 MB read, 10.7 s), and exact lookups without the object cache made 149 small requests (18.5 s). With the cache, a brand-new list took 5.1 s cold and 0.9 s on reload (measured 2026-10-26). The `IN` version is only a fallback if a future DuckDB-WASM upgrade makes this slow.
- **Browser measurements (sessions 16 and 18):** warm queries take 50 to 100 ms; 997 to 12,291 Australians compute in 286 to 509 ms warm. Sorting `persons` and `ranks_*` by `wca_id` (step 8) cut the read for a 19-person list from 22.6 MB to 9.8 MB. `persons.parquet` carries `country_iso2`, so browser-built rankings show flags; `ranks_*` come from the export (up to a day old).
- **Cost notes:** storage is far below the free limit (the whole results set is about 170MB). The realistic risk is request counts on a public r2.dev URL (bots, many queries); consider a Cloudflare custom domain (cached responses don't count as R2 reads) and a Cloudflare usage notification. Supabase free has hard caps rather than per-GB billing: 500MB database, 1GB file storage (list JSON is roughly 250MB, about 200MB of it state lists, so moving state history to Parquet also frees Storage).

**Content-Security-Policy (session 19, 2026-10-26).** Every HTML page, including `auth-callback.html`, carries the same `<meta http-equiv="Content-Security-Policy">` tag straight after `<meta charset>` (GitHub Pages cannot send headers, and a meta tag cannot do `frame-ancestors` or Report-Only). The policy: `default-src 'self'`; `script-src 'self' https://esm.sh https://cdn.jsdelivr.net/npm/ 'wasm-unsafe-eval'` (supabase-js, DuckDB-WASM, WebAssembly); `worker-src blob:` (DuckDB starts its worker from a `blob:` URL); `connect-src 'self'` plus the Supabase project URL, the `wca-parquet` Worker, the `r2.dev` bucket, `https://cdn.jsdelivr.net` (the `.wasm` file) and `https://www.worldcubeassociation.org` (WCA API); `img-src 'self' data: https://*.worldcubeassociation.org` (avatars); `style-src 'self' 'unsafe-inline'` (the pages and the JS write `style="…"` attributes; styles cannot run script); `font-src 'self' data:`; `object-src 'none'`; `base-uri 'none'`; `form-action 'self'`. **Rules that follow from it:** (1) no inline `<script>` blocks and no `onclick=`-style attributes in any page: put the code in a file under `docs/js/` (the `*-boot.js` files exist for this); (2) a new third-party host (a font, an image host, another CDN) must be added to the tag in **every** page, otherwise the browser blocks it with a "Refused to …" console message that names the directive and the host; (3) with DevTools open the console shows blocked `esm.sh/….mjs.map` requests: these are source-map lookups made by DevTools, not by the site, and are harmless (self-hosting supabase-js would remove them and let `esm.sh` leave the policy). (The only console messages after the CSP went live were those `.mjs.map` ones.)

### Rankings page overview
Loaded JSON lives on the `store` object, UI selections on `state`. Each tab module has `render*()` functions that rebuild their DOM from `store`. `main.js` resolves the data source, fetches everything with `loadData()`, then draws the visible tab (see "Lazy drawing" below; `renderAll()` no longer exists).

Shared helpers: `renderTable` (generic table from column definitions; wraps itself in `.scroll-table`), `renderDetailedTable` (per-event breakdown table used by SoR, Kinch, Top 100, FAR counts; wraps its table in a `.scroll-table` div), `esc` (exported; escapes `& < > " '`), `nameLink` (clickable name → profile; **escapes both arguments itself**, so callers pass the plain name and must NOT call `esc` first or it shows "&amp;"), `eventIcon` (every place an event name is displayed goes through it; it escapes its label), `populateEventSelect` (builds the row of event-icon buttons), `formatResultLike` (client-side result formatter, incl. FMC and Multi-Blind), `formatDate` (renders "1st January 2023"), CSV export via `data-container` buttons (a cell starting with `=` or `@`, or `+`/`-` followed by a letter, gets a leading apostrophe so spreadsheets do not run it as a formula).

**State lists on this page (10b):** they load through the same code, with `body.state-mode` (see "Data source resolution"). The Members tab skips WCA avatar fetching (`store.listKind === 'state'`). The biggest states may still have thousands of people and `rankings.json` files of 10MB+, so large tables may render slowly (not yet measured).

### Tables and the stylesheet
- `style.css` is organised into labelled sections. Layout variables live in `:root`: `--page-max` (1400px content width, also used by the footer), `--rank-col-w`, `--icon-col-w`, `--thead-row-h`.
- **`.scroll-table`** is the wrapper for wide tables. It scrolls inside its own box (both directions, height capped to roughly the viewport), keeps the **header row pinned to the top**, and pins the **first columns to the left**: `#` then Name in detailed tables (`td.rank-cell`, `th:has(+ th.name-header)`, `.name-cell`, `.name-header`; the `#` + Name freeze uses `:has()`), icon + event name in a records table. Corner cells get a higher z-index so they sit above both. A `.scroll-table` nested inside another becomes a plain wrapper, so the outer one does the scrolling and the sticky cells still work. Sticky needs `border-collapse: separate`, so the border sits on the wrapper. `.scroll-table` forces `white-space: nowrap`.

### Data source resolution (`main.js`)
- `resolveSource()` dynamic-imports `auth.js`, calls RPC `get_list_by_slug(LIST_ID)`, and on success uses the list uuid + list row (including `data_level`, `owner_id`, `kind`, `official_names_only`; since 10a also `country` and `region`). If the lookup fails it throws a friendly error ("List not found. If it is private, log in…").
- `fetchJson(file, required)` reads `supabase.storage.from('list-data').download('<uuid>/<file>')`. A missing required file on a list whose `data_level` is `none` shows "This list is still being built. Check back in a few minutes." (A state list whose first build hasn't finished shows a 404-style load failure or this note.) **Since session 16 this message only appears when the instant path below can't run** (no readable members, or an error).
- **Instant rankings (session 16).** `loadData()` calls `loadInstant()` right after the state-mode setup: for a non-state list with `data_level = 'none'` it dynamic-imports `instant-rankings.js`; on success `rankings`, `individual` and `historical` come from the browser, the optional files are null and `meta` is `{level: 'basic'}` (so the "full history is still being processed" note shows), and the footer reads "Calculated in your browser in N s from the latest WCA export (official ranks may be a day behind)." Any failure is logged (`Instant rankings unavailable`) and the page falls back to fetching the built files and the old message. Once the build finishes (`data_level` is no longer `none`) the next page load uses the built JSON (no automatic switch while the page is open). Flags (step 8): `instant-rankings.js` reads `country_iso2` from `persons.parquet` and sets `countryIso2` on the people and on the output rows (it falls back to no flags if an older Parquet copy lacks the column). Limits: names are owner-typed `display_name` or the official name only (preferred-name rules stay in `sync-lists.js`, but the viewer's own "only me" name still applies through `applyOwnName`), official ranks come from the export copy (up to a day old), and who can see it follows the normal permissions (a non-member of a private list, or a logged-out visitor of an unlisted list whose members can't be read, gets the old message). To test it without waiting for a build: `update public.lists set data_level = 'none', built_at = null where slug = '<slug>';` (this does not bump `dirty_at`, so no build starts until the next scheduled run or a manual `pending` run), then open the rankings page; the Network tab filtered on `parquet` shows the requests (tick Disable cache and hard-reload for cold numbers). Reset the list afterwards with `update public.lists set dirty_at = now() where slug = '<slug>';` (that starts an on-demand build back to `full`).
- After the list is found: `setupEditLink(list)` (not awaited; returns early for personal and state lists) shows the side-menu **Edit this list** link; after the JSON loads, `applyOwnName(...)` applies the "only me" name overlay; then `store.personal` and `store.personalListId` are set from the list row; for a personal list `enterPersonalMode()` runs at the end of `loadData()`.
- `loadData()` ends by caching the live data in `store.live` (`rankings`, `individual`, `historical`, `streaks`) and calling `restoreTimeTravel(refreshAll)`, which re-applies any saved On This Date / Time frame from the site settings (skipped on state lists). **State mode (10b):** right after `resolveSource()`, `loadData()` sets `store.listKind` (`group`/`personal`/`state`). For `state` it adds `body.state-mode` (CSS at the end of `style.css`; since session 13 it hides only Rolling (menu item and Home link), the Home members chips and Recent activity, because the state build makes no `rolling-averages.json` or `recent-activity.json`; Results, Misc (including PR Streaks, Event Streaks and Upcoming) and the profile tabs are shown. Known rough edges: the Random statistic button and the profile's Rolling sub-tab can still land on empty parts), shows the side-menu **All states** link (`#states-link`, → `states.html`), skips `renderHomeMembers()` and skips `restoreTimeTravel`, so a saved date view is ignored on state lists.
- **Lazy drawing (2026-10-28).** `loadData()` no longer draws every tab. Once the data is in, `setupLazyRendering()` starts a `MutationObserver` on every `.tab-panel` and every `#tab-misc > .subtab-panel` (watching only their `class`), and `renderVisible()` draws the groups the visible panels need. `LAZY` (in `main.js`) maps a panel's element id to render groups (`tab-home`, `tab-records`, `tab-events`, `tab-individual`, `tab-overall`, `tab-members`, and the Misc statistics `subtab-top100`, `-farcounts`, `-age`, `-streaks`, `-streaks-event`, `-prcount`, `-history`, `-h2h`, `-nemesis`, `-chasing`, `-podiums`, `-subx`, `-attendance`, `-whatif`); `RENDER` maps each group to the function(s) that draw it. A group is drawn once (the `rendered` set) the first time its panel is `active`, however the tab was opened (side menu, Home link, Members button, Random statistic), and logs `Drew "<group>" in N ms` to the console. `refreshAll()` (the callback time travel receives) repopulates the selects, clears `rendered` and redraws only what is visible; other tabs redraw when next opened. A group that throws is logged (`Could not draw "<group>"`) and the rest of the page keeps working. **Not lazy:** Upcoming, Recent activity, Improvement, Consistency and Rolling are drawn once at load (they always show live data, time travel never redraws them, and they cost about 40 ms on a laptop). A panel id missing from `LAZY` is never drawn by this mechanism. `ui.js` is unchanged by all this.
- **List lifecycle ping (session 15):** at the very end of `loadData()`, `main.js` dynamic-imports `list-activity.js` and calls `recordListOpen(source)` (not awaited, errors swallowed). It only acts for `kind = 'group'` lists with an owner and a logged-in viewer, at most once a day per user and list (localStorage `fa-list-opens`), and calls RPC `record_list_open`; the database only counts it when the viewer is the owner or a member (section 6).
- **Wiring order matters:** `setupStatsList()` must run **before** `setupSubtabs('misc-subtabs')` (it builds the Misc rows that `setupSubtabs` attaches handlers to).

### Compare (`tabs/compare.js`)
Exports `populateCompareSelects` (mounts the pickers), `renderHeadToHead`, `renderNemesis` (calls `renderTrueNemesis` and `renderChasing`). Everything reads `store.rankings`, so On This Date and the Time frame work automatically.
- **Head-to-Head:** 2 to 5 people (`h2h-person-1` … `-5`, all five optional, each cleared with the × of its picker), a Single / Average / Kinch toggle (`h2h-view-toggle`). Events are rows, people are columns. An event is shown only if **everyone selected has a single** in it (Average view also needs the event to have an average; a person without an average shows "—"). The best value in each row is gold (ties are all gold; Kinch is higher-is-better). Fewer than two different people shows "Pick at least two different people".
- **Nemesis (true nemesis):** person B is a nemesis of person A if, for **every single and average result A has**, B has a **strictly better** (not equal) one. A result A has that B lacks means B is not a nemesis. Events A has nothing in are ignored. The view reads "N nemeses" (the goal is 0) with a list, plus "is the nemesis of K people".

- **Person pickers (2026-10-30, `js/person-picker.js`):** `mountPersonPicker(select, {getPeople, allowBlank, defaultToMe, placeholder})` hides a `<select>` and puts a type-to-search box in front of it (matches name or WCA ID ignoring accents, names that start with the text first, at most 50 shown with a "keep typing" note; arrow keys, Enter, Escape; × clears when `allowBlank`). Used by Head-to-Head, Nemesis, Chasing and the Kinch What-If. `getMyWcaId()` (cached, one `profiles` lookup per page load) backs `defaultToMe`: Nemesis, Chasing and the What-If start on the logged-in user if they are on the list and have not picked anyone; Head-to-Head box 1 does the same in `compare.js` (and moves box 2 if it was the same person). To use it on a new person dropdown: keep an empty `<select id="…">` in `index.html`, call `mountPersonPicker` from the populate function (it must run again after time travel), and keep listening for `change`.

### Round names

## 5. Key formulas

- **Sum of Ranks** — per event, people with results are ranked 1..k as usual; everyone without a result ties at k+1. Single and average tracked separately.
- **Kinch Rank** — one combined score, not separate single/average.
  - Most events: score = group best average ÷ person's average × 100.
  - Blindfolded events (3BLD, 4BLD, 5BLD) and FMC: take whichever of single/average scores higher.
  - Multi-Blind: single only. Raw score = `(solved − missed) + fraction of the hour remaining`, then ratioed against the group's best raw score.
  - Overall = mean across all events. (For a state list "group" means the state's people.)
- **PR streaks** — primary metric is cross-event: consecutive COMPETITIONS with a PR in ANY event. **A tie with the previous best counts as a PR** (also in the round-level side panel and in time travel / the Time frame). "Best ever" shows every streak that beat the person's previous longest, not just the longest overall. "Current" is the streak still running. The per-event, round-level version is a "fun stat" side panel. Under a Time frame, PRs are still judged against all earlier results but only competitions inside the frame form the streak (section 4).
- **Rolling averages** — ranked like Event Rankings; each entry labelled by source (first solve → last solve). Formats mo3/ao5/ao12/ao25/ao50/ao100 selectable for every event. Multi-Blind excluded. Default format: ao5, or mo3 for 6x6, 7x7, FMC, 4BLD and 5BLD.
- **Improvement** — each person's best as of date A vs date B for a chosen event/type, sorted by most improved.
- **PR counting** — each person's best "counting" solve. In a five-attempt round the best and worst solves are dropped, so a round's counting solve is its second-fastest solve; the person's value is the best of those across all their rounds. Only events with a five-attempt average (excludes 333mbf, 333bf, 444bf, 555bf, 666, 777, 333fm). Example: rounds `(8.00) 9.50 9.00 10.00 (10.50)` and `9.50 (8.50) 9.50 (11.00) 10.25` give 9.00.
- **Nemesis (Compare)** — B is a nemesis of A when B is strictly better than A in every single and every average A has a result for; a result A has that B lacks disqualifies B. 0 nemeses is the goal. (Chasing is just "the person ranked directly above you".)
- **Psych sheet order (Upcoming)** — within an event, registered members sort by group average rank, then group single rank, then name; events without an average sort by single rank.
- **State assignment (state lists)** — see section 1, "State lists": override first (hidden / chosen region); otherwise, for people whose WCA country is a built country, the region with the most distinct competitions in the last 3 years (min 2), falling back to all time (min 2); ties → region of the most recent competition; nobody else.
- **Events with an average:** every event except Multi-Blind (`SINGLE_ONLY_EVENTS` in `scripts/lib/events.js`). 3BLD, 4BLD and 5BLD have an official mean/average of 3 (4BLD/5BLD were wrongly treated as single-only until 2026-10-14).

### Where names come from in a build
`sync-lists.js` writes each member's resolved `displayName` into `build/lists/<slug>.json` (rules in section 4, "Display names"), after `cleanName()` has removed `<`, `>`, `"` and control characters. `extract-bests-from-parquet.py` (and the fallback `fetch.js`) use it as the person's `name` (falling back to the official WCA name); `parse-export.js` and `fetch-upcoming.js` use it too. So the name reaches every output file. State lists get names from `states-input.json` instead (`build-states.js`).

## 6. Backend: Supabase (accounts, lists, list data)

Free tier, hosted. Chosen for: free, low maintenance, row-level security for private lists, standard Postgres (portable, and fits the long-term database plan).

### Schema (`supabase/schema.sql`)
- `profiles` — one row per logged-in person: `id` (= auth user id), `wca_user_id` (unique, not null), `wca_id` (nullable: WCA accounts with no competitions have none), `name` (official WCA name), plus display-name settings: **`preferred_name`** (nullable, max 40 characters) and **`name_visibility`** (`me` default | `lists` | `everywhere`). The login Edge Function writes only `id`, `wca_user_id`, `wca_id`, `name`, so a re-login never clears the display-name settings. The browser can read only its own row.
- `lists` — `id`, `slug` (unique, `^[a-z0-9-]{2,40}$`), `name` (1–80 chars), `owner_id` (**nullable**: null means a guest list or a state list), `visibility` (`public` | `unlisted` | `private`, default `private`), timestamps, build tracking (`dirty_at`, `built_at`, `data_level` `none`|`basic`|`full`), **`kind`** (`group` default | `personal` | `state`), **`official_names_only`** (boolean, default false) and, since 10a, **`country`** (ISO2) and **`region`** (code like `NSW`). A list is **pending** when `built_at` is null or older than `dirty_at`. **Since session 15:** `last_opened_at` (timestamptz, not null, default now(); every existing list got the migration time) and `permanent` (boolean, default false). Neither is in the column-level update grant, so they change only through `record_list_open`, `set_list_permanent` and `expire_lists`. Triggers: `trg_b_reserved_slugs` (session 14, `reject_reserved_slugs()`, before insert, after `trg_a_lists_kind`): a `kind = 'group'` list (guest lists included) cannot have a slug starting `state-` or `me-`, because those belong to state lists and personal profiles; existing lists are not affected.
  - Constraint `guest_lists_unlisted`: `owner_id is not null or visibility = 'unlisted'`.
  - Constraint `lists_kind_check`: kind in (`group`, `personal`, `state`). Constraint `lists_state_fields`: a `state` list must have country, region and no owner. Unique index `lists_state_unique` on (country, region) where kind = 'state'.
  - Owners can directly update only `name`, `visibility` and `official_names_only` (column-level grant; update was revoked for `authenticated`/`anon` on the rest).
  - Trigger `trg_lists_names_dirty` bumps `dirty_at` when `official_names_only` changes. Trigger `trg_a_lists_kind` (named `a` so it runs first) forces `kind = 'group'` for inserts made by `authenticated`/`anon`, so only `create_my_profile()` (personal) and SQL / the service role (state) can make other kinds.
  - The eight Australian state lists are seeded by `005_states.sql`: slugs `state-au-nsw|vic|qld|wa|sa|tas|act|nt`, names "New South Wales", "Victoria", "Queensland", "Western Australia", "South Australia", "Tasmania", "Australian Capital Territory", "Northern Territory", `unlisted`.
- `list_members` — `(list_id, wca_id)` primary key, optional `display_name`, `added_at`. Members are **WCA IDs, not accounts**, so people can be on a list before they ever log in; logging in with a matching WCA ID is what puts a list in "Lists I'm in". Members can read their own row of a list they can view (used by the "only me" overlay check). State lists have no members.
- `list_opt_outs` — `(list_id, wca_id)` primary key, `created_at`. RLS enabled with **no policies**: only security-definer functions touch it.
- `guest_edit_tokens` — `list_id` (primary key, cascade delete with the list), `token_hash` (SHA-256 hex), `edited_at`. RLS enabled with **no policies**.
- `preferred_name_lists` — `(list_id, wca_id)` primary key: the lists a person chose to show their preferred name on (used when `name_visibility = 'lists'`). RLS enabled with **no policies**: only functions and the service role touch it. Rows are not cleaned up if the person later leaves the list (harmless).
- **`person_regions`** (10a) — `wca_id` (primary key), `country`, `region` (nullable), `hidden` (true = left out of state rankings; check `hidden or region is not null`), `updated_at`, `updated_by` (profile id, set null on delete). No row = use the automatically detected region. Keyed by WCA ID, so it works for people who never logged in. RLS enabled with **no policies**: only functions and the service role (the build) touch it. **Last write wins** between the person and an admin.
- **`admins`** (10a) — `wca_id` (primary key), `added_at`. RLS enabled, no policies. Filled by hand in the SQL Editor (`insert into public.admins (wca_id) values ('…'), ('…') on conflict do nothing;`) with the owner's and one other person's WCA IDs; matched against `profiles.wca_id` of the logged-in user, so both just log in with WCA as normal.
- Helper functions (security definer, avoid RLS recursion): `current_wca_id()`, `is_list_owner()`, `can_view_list()`, `can_read_list_data(folder text)`, and (10a) **`is_admin()`** (true when the logged-in profile's WCA ID is in `admins`; execute granted to `authenticated` only). **Since 10c `can_view_list()` is also true for admins on any non-personal list** (so `get_list_by_slug`, `members_select` and the Storage read policy open private group lists to them), and **`is_list_owner()` is also true for an admin on any owned group list** (`kind = 'group'`, `owner_id` not null), which opens the members policies. Personal profiles stay private to their owner and guest lists aren't admin-editable.
- RPCs: `my_lists()` (every list I own or belong to, **including my personal list**), `lists_i_am_in()` (membership only, any visibility), `get_list_by_slug()` (public/unlisted open to anyone holding the slug; returns the `lists` row including `country`/`region`), `leave_list(p_list)`, `undo_opt_out(p_list)`, `my_opt_outs()`. `mark_list_built(p_list, p_dirty, p_level)` is **service role only**.
- Name and profile RPCs (`authenticated` only): `set_name_settings(p_name, p_visibility, p_lists uuid[])` (validates, saves the name and visibility, replaces the chosen lists, marks every list the person is on pending), `my_name_lists()` (returns the list uuids they chose), `create_my_profile()` (creates the one private `personal` list `me-<wcaid lowercase>` named after the official name with the person as its only member, or returns the existing one). The older `set_preferred_name(text)` was dropped.
- **Region RPCs (10a, all `authenticated` only):**
  - For the logged-in person (their own WCA ID): `get_my_region()` → rows of `(country, region, hidden)` (empty when there is no override), `set_my_region(p_country, p_region)`, `hide_me_from_regions()` ("remove me from state rankings"), `clear_my_region()` (back to automatic). Used by `states-page.js` (10b).
  - For admins (raise "Admins only" otherwise; any WCA ID): `admin_get_region(p_wca_id)`, `admin_set_region(p_wca_id, p_country, p_region)`, `admin_hide_region(p_wca_id)`, `admin_clear_region(p_wca_id)`.
  - **Admin RPCs (10c; admins only, execute granted to `authenticated`):** `admin_get_name(p_wca_id)` → `(preferred_name, name_visibility)` (empty when the person has no profile), `admin_set_name(p_wca_id, p_name)` and `admin_clear_name(p_wca_id)` (only for a name set to `everywhere`), `admin_list_overview()` (every `kind = 'group'` list with an owner: slug, name, visibility, owner name and WCA ID, member count, build status; personal profiles and guest lists are left out) and `admin_list_regions()` (all `person_regions` rows, newest first). Internal (execute revoked): `clean_display_name(text)`, `mark_person_dirty(wca_id)`.
  - **Admin edits through the tables (10c):** policies `lists_update` / `lists_delete` are `owner_id = auth.uid() or (owner_id is not null and kind = 'group' and is_admin())`; the column-level update grant (`name`, `visibility`, `official_names_only`) still applies, and `block_opted_out` and the member limits still apply to admins.
  - Internal (execute revoked from everyone): `valid_region(country, region)` (AU: NSW, VIC, QLD, WA, SA, TAS, ACT, NT — extend it per country), `mark_state_lists_dirty(country)`, `apply_region(...)`, `clear_region(...)`. Every change marks that country's state lists dirty (and the old country's if it changed).
  - **The detected (automatic) region is not stored in the database**: it exists only inside the built data. It is exposed to the browser through `state-assignments.json` in the state lists' Storage folders (10b, section 3).
- Guest RPCs (callable by `anon` and `authenticated`, except claim): `create_guest_list(p_name, p_slug, p_members jsonb, p_token)`, `get_guest_list(p_slug, p_token)` (returns `{list, members}`), `update_guest_list(p_slug, p_token, p_name, p_members)`, `delete_guest_list(p_slug, p_token)`; `claim_guest_list(p_slug, p_token)` is `authenticated` only. Internal helpers (execute revoked from everyone): `guest_clean_members(jsonb)`, `guest_list_id(slug, token)`. `guest_hash(text)` = SHA-256 hex.
- RLS policies:
  - `lists_select` (SELECT): `owner_id = auth.uid() or visibility = 'public' or can_view_list(id)`. **The direct owner/public checks are required**: with only `can_view_list(id)`, creating a list failed with "new row violates row-level security policy for table lists". (Recorded in `schema.sql`.) State lists (unlisted, no owner) are therefore not readable through the table; they are reached through `get_list_by_slug`.
  - `lists_insert`: `owner_id = auth.uid()`. `lists_update` / `lists_delete`: `owner_id = auth.uid()`. (A null owner never matches, so guests can't touch lists through the tables.)
  - `members_select`: `can_view_list(list_id)`. `members_insert` / `members_update` / `members_delete`: `is_list_owner(list_id)`.
  - Unlisted lists are not enumerable through table reads.
- **List lifecycle (session 15; SQL in `schema.sql`, from `session15-lifecycle.sql`).** Applies only to `kind = 'group'` lists that have an owner (personal profiles, state lists and guest lists are never touched; guest lists keep their own 90-day purge). Three tiers, by `last_opened_at`:
  - **Active** (opened in the last 30 days): built as usual.
  - **Dormant** (not opened for 30+ days, not permanent): `sync-lists.js` leaves it alone in `--built` (daily) and `--all` (weekly, and the Upcoming scan) as long as it is fully built and has no pending edit; its old JSON stays in Storage. `--pending` never skips anything, so an edit rebuilds it as always. A dormant list's data can be a month or more old until someone opens it.
  - **Expired** (not opened for 90+ days, not permanent): deleted by the weekly cleanup. The day counts are in three places that must change together: `record_list_open()` (30), `expire_lists()` (90) and `sync-lists.js` (`DORMANT_DAYS` = 30) / `lists-page.js` (`EXPIRY_DAYS` = 90).
  - **What counts as an open:** only a logged-in viewer who is the list's owner or a member (decided 2026-10-22), through `record_list_open(p_list)` (execute: `authenticated`), at most once a day (server check on `last_opened_at`, plus the browser throttle in section 4). Anyone else, a guest, or a non-member viewing a public link does not count. Opening a **dormant** list also bumps `dirty_at`, so the on-demand trigger rebuilds it straight away.
  - **Permanent:** `set_list_permanent(p_list, p_permanent)` (owner or admin; execute: `authenticated`). Owners can have at most **10** permanent lists (`v_max` in the function; admins have no limit, so an admin never sees the limit error); setting or removing permanence resets `last_opened_at`. FA (`slug = 'fa'`) was made permanent by the migration.
  - **Cleanup:** `expire_lists()` (service role only) deletes expired lists in one statement and returns their ids (members, opt-outs and name choices cascade). `scripts/cleanup-lists.js` (weekly `full` run, before the sync, `continue-on-error`) calls it, then lists the top-level folders of the `list-data` bucket and deletes every folder whose uuid is not in `lists` (so it also removes leftovers of deleted lists and purged guest lists). Safety: folders are listed before the list ids are read, nothing is deleted if no lists could be read, at most 500 folders per run. Expiry can therefore be up to 7 days late (the lists page shows "Expires soon" meanwhile).
  - **Notices:** owners see "expires in N days" only when 14 days or fewer remain (no email).
- Triggers/limits: 20 **group** lists per owner (`limit_lists`, personal lists don't count; `claim_guest_list` checks the same limit itself); 100 members per list (`limit_members`); `touch_updated_at`; `mark_list_dirty` (after any insert/update/delete on `list_members`, sets `lists.dirty_at = now()`); `block_opted_out` (before insert on `list_members`).
- **On-demand build trigger (session 12, appended to `schema.sql`; there is no separate migration file):** function `trigger_build()` (security definer) calls GitHub's `workflow_dispatch` for `update-custom-lists.yml` (ref `main`, mode `pending`) through `pg_net`, reading the GitHub token from the Supabase Vault secret `gh_workflow_token`. Statement-level triggers on `lists`: `build_on_list_insert`, and `build_on_list_update` (fires only when some list's `dirty_at` changed, so `mark_list_built` does not loop). Since `mark_list_dirty` bumps `dirty_at` on any `list_members` change, member edits, name changes, region changes and new personal profiles all start a build. See section 1, "On-demand builds".
- **Name safety (session 19, `supabase/session-19-name-safety.sql`; append it to `schema.sql` if that has not been done yet):** function `is_safe_name(text)` (immutable; no `<`, `>`, `"`, no control characters; null is fine) and CHECK constraints `list_members_display_name_safe` (also at most 60 characters), `lists_name_safe` and `profiles_preferred_name_safe`, added `NOT VALID`, then a one-off cleanup `UPDATE` of existing rows, then `VALIDATE CONSTRAINT`. The constraints matter because owners write `list_members.display_name` and `lists.name` straight through the table policies, so checks inside functions never see them (violations have error code `23514`; `lists-page.js` `friendlyError` shows a readable message). `clean_display_name`, `set_name_settings` and `guest_clean_members` were replaced to give friendly messages. `profiles.name` (the official WCA name written by the Edge Function) is deliberately not constrained, so a login can never fail on it.
- Not yet in the schema: ownership transfer; admin management (admins are added and removed by hand in the SQL Editor, by design); admin access to personal profiles and guest lists (deliberately excluded).

### Guest list limits
- **One per browser**, enforced client-side only; clearing browser storage lets someone make another and loses edit access to the old one.
- Server-side: 30 members per guest list, **200 guest lists in total** (counts `kind = 'group'` ownerless lists only, since 10a), and a guest list is **purged after 90 days with no edits** (the purge runs at the start of every `create_guest_list` call).
- Known leftovers: purged or deleted guest lists leave their built JSON in the private Storage bucket until the weekly cleanup sweep removes it (session 15); anyone holding the public key can fill the 200 slots by calling the function directly (the fix would be a captcha, deliberately not built).

### Opt-out semantics
`leave_list` deletes the caller's `list_members` row (matched via `profiles.wca_id`) and records an opt-out row, so the owner cannot re-add them. The person can reverse this from "Lists I've left" (`undo_opt_out`). Logged-in users with no WCA ID can't be members of anything. A person who opts out stays in the rankings until the next build finishes. (State rankings have their own opt-out: `hide_me_from_regions()`.)

### Storage (`list-data` bucket)
- Private bucket, 50MB file limit, `application/json` only.
- Objects are at `<list uuid>/<file>.json`. Policy `list_data_read` (select only) allows read when `can_read_list_data(folder)`: public and unlisted lists (guest lists and state lists included) are readable by anyone who knows the list uuid, private lists (personal profiles included) only by the owner and members (`can_view_list`).
- No insert/update/delete policies: only the service role (the build job) writes.
- `upload-lists.js` minifies and refuses files over 45MB, so per-list size needs capping if a list gets very large (watch the biggest state lists). Its `FILES` list includes `upcoming.json`, `state-assignments.json` and `state-unassigned.json`.

### Login flow (Edge Function `wca-auth`)
1. `auth.js startWcaLogin()` stores a random `state`, sends the browser to WCA `/oauth/authorize` with `redirect_uri = <SUPABASE_URL>/functions/v1/wca-auth`, scope `public`. The page it was on (`location.href`) is saved in sessionStorage `wca-return-to`, so login from `home.html`, `lists.html`, `states.html` or a rankings page returns to that page.
2. WCA redirects to the function with `code` + `state`.
3. Function exchanges the code (using the client secret), calls `/api/v0/me`, creates the Supabase user if needed (made-up permanent email `wca-<wcaUserId>@wca-login.invalid` — never receives mail), generates a one-time magic-link token, upserts the `profiles` row (name and WCA ID refreshed every login; the upsert only writes the columns it sets).
4. Function redirects to `<SITE_URL>/auth-callback.html?token_hash=…&state=…`; `finishLogin()` checks `state` and calls `verifyOtp` to create the real session.

### Settings that must stay as they are
- Function `wca-auth` deployed with JWT verification off / no API-key requirement (WCA's redirect can't send one). It is public by design; it only acts on a valid WCA code.
- Supabase Auth: the **Email provider must stay enabled** (login hand-off uses it). "Allow new users to sign up" can be off — users are created via the admin API.
- WCA application: redirect URI exactly `<SUPABASE_URL>/functions/v1/wca-auth`, scope `public`.
- Function secrets: `WCA_CLIENT_ID`, `WCA_CLIENT_SECRET`, `SITE_URL` (GitHub Pages address, no path beyond `/fa`). `SUPABASE_URL` and the service key are supplied automatically.
- GitHub repository secrets (for `update-custom-lists.yml`): `SUPABASE_URL`, `SUPABASE_SERVICE_KEY`, and since session 11 `R2_ENDPOINT_URL`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`.
- **Vault secret `gh_workflow_token`** (session 12): a fine-grained GitHub token, repository `fa` only, Actions read/write, created by hand with `vault.create_secret(...)` in the SQL Editor (the line is not in the repo). `pg_net` must stay enabled. If the token expires or is deleted, on-demand builds stop silently and only the slow schedule remains.
- Cloudflare R2 bucket `wca-parquet-data`: public access (r2.dev URL) must stay enabled and the CORS rule described in section 1 ("Parquet pipeline") must stay, or DuckDB-WASM in the browser and the pending builds' `https://` reads stop working. Never store private data there. The Worker `wca-parquet` (address in section 1, "Parquet pipeline") needs its R2 binding named exactly `BUCKET` (the script reads `env.BUCKET`); keep `r2.dev` enabled while builds and the `db.js` fallback use it.

### Security rules
- The **publishable** key and WCA application ID are public and live in `supabase-config.js`. The **secret/service-role** key and the **WCA client secret** never go in the repo, `docs/`, or a chat. The service key lives only in the Supabase dashboard and GitHub Actions secrets.
- `supabase-admin.js` sends the key in the `apikey` header, and also as `Authorization: Bearer` only when it starts with `eyJ` (legacy JWT-style keys). The newer `sb_secret_...` keys are not JWTs.
- Private list data must never be written to `docs/` (public repo). Builds write to git-ignored `build/` (the workflow has no commit permission) and upload to private Storage.
- All permission checks are in database RLS/functions/Storage policy, not client code. **Admin checks are only ever `is_admin()` inside security-definer functions** (and, since 10c, the `lists_update` / `lists_delete` policies); the browser can never write `admins`, and the "Admin view" button is only a convenience.
- Guest edit tokens: only the SHA-256 hash is stored server-side; the raw token exists only in the guest's browser and in the RPC call. See section 9, "Security review" for what was audited and the owner's remaining dashboard checks.
- **Names are untrusted text** (anyone can type one): constraints in the database, `cleanName()` in the build, escaping when drawing (section 4, "Display names", "Name safety").
- **Content-Security-Policy** on every page and no inline scripts (section 4, "The six pages").

## 7. Deploy rules

- **Client-only change** (`docs/js/`, the HTML pages, `style.css`, `auth-callback.html`, `docs/img/`): replace the touched files on the GitHub website, commit, push. No workflow re-run needed. **Every HTML page must keep its CSP meta tag and contain no inline `<script>` or `onclick=`-style attribute** (section 4, "The six pages"); put new page code in a `js/*-boot.js` file and create it before pushing the page that loads it.
- **New files must be created in the repo** (GitHub: Add file → Create new file, with the full path). **A statically imported module that is missing breaks every page that loads it** (e.g. a missing `name-settings.js`, `home-members.js`, `datepicker.js`, `tabs/upcoming.js`, `tabs/stats-list.js` or `timetravel/storage.js` breaks all rankings pages; a missing `timetravel/storage.js` or `datepicker.js` also breaks `settings.html`; a missing `states-page.js` breaks `states.html`; a missing static import of `lists-page.js` shows "Could not load lists."). Create new modules **before** pushing the files that import them. Optional features (the profile card, `home-page.js`, `lists-page.js`) are loaded with a guarded dynamic import so they can't blank a page.
- **File names must match the references exactly** (e.g. `js/theme.js`, not `themes.js`): a wrong name fails silently with a 404 and the page just loses its colours.
- **A module error naming a missing export** ("does not provide an export named …") means the file the browser loaded is not the file that was sent (a short paste or a cached copy): check the end of the file on GitHub, then hard refresh.
- **Build script or data-shape change** (including `parse-export.js`, `fetch.js`, `extract-bests-from-parquet.py`, `fetch-upcoming.js`, `sync-lists.js`, `build-states.js`, `scripts/lib/events.js`): replace `scripts/` and/or `.github/` as needed, commit, push, then re-run **Update Custom Lists** from the Actions tab (mode `full` when a new field, event definition or history file changes, or to repair data after a bad run; `bests` to refresh Upcoming; `pending` for new/edited lists and state lists). New data fields only appear after that rebuild; client code should fall back gracefully until then.
- **Parquet pipeline change** (`convert-to-parquet.py`, `extract-from-parquet.py`, the Parquet/R2 steps or the Full build step in the workflow): push, then run **Update Custom Lists** in mode `full` (it converts, uploads to R2 and builds from the fresh files; you can cancel once the "Full build" step finishes, since the 9-minute Upcoming step comes last). In the log look for `Building full-results.json from Parquet`; `falling back to parse-export.js` means the extractor failed. Changing the Parquet columns means changing converter and extractor together, and the R2 copy only updates on the next `bests` or `full` run. Give the workflow as a full file and check it still has every step (Full build, upload and mark, Upcoming): an earlier AI-assisted edit silently dropped them. **Watch the DuckDB version:** the workflows run an unpinned `pip install duckdb`, and DuckDB 2.0.0 (seen 2026-10-25) rejected the old `x -> ...` lambda syntax in `convert-to-parquet.py` (fixed by writing `lambda x: ...`). If another DuckDB release breaks a script, `pip install "duckdb<2"` is the quick fix.
- **On-demand build change** (the trigger SQL in `schema.sql`, the token): run the SQL from `schema.sql` in the SQL Editor (appending it to the repo file does not change the database), create or replace the Vault secret by hand, and make sure the workflow file with `workflow_dispatch` is on `main`. To test, create a list or edit a member, then check `select status_code, content from net._http_response order by created desc limit 5;` (204 = success) and the Actions list.
- **Worker changes** are pasted into the Cloudflare dashboard (Edit code, then deploy), not pushed. A page that still behaves the old way after a push usually means a file didn't land: open `https://mogomonx.github.io/fa/js/<file>.js?x=1` and search for a recent string.
- **List lifecycle change** (session 15): run the SQL (`session15-lifecycle.sql`, then append it to `schema.sql`) **before** pushing code, because `sync-lists.js` now selects `owner_id`, `permanent` and `last_opened_at` and fails without them. Push the new files (`scripts/cleanup-lists.js`, `docs/js/list-activity.js`) before the files that use them. To check status: `select slug, permanent, last_opened_at, dirty_at, built_at, data_level, round(extract(epoch from (now() - last_opened_at)) / 86400, 1) as days_since_open, case when kind <> 'group' or owner_id is null then 'n/a' when permanent then 'permanent' when last_opened_at < now() - interval '90 days' then 'expired' when last_opened_at < now() - interval '30 days' then 'dormant' else 'active' end as tier from lists order by last_opened_at;`. ### Loading speed (reported and fixed 2026-10-27; more needed before WCA-wide data)
**What happened.** The owner saw Victoria's state page load slowly and inconsistently after publishing. `main.js` now prints two console tables after each load (the load steps, and each file's download / read / parse time), which found the cause: the **Improvement tab's first render took about 8.5 s** of a 12.3 s load. `renderImprovement` scanned all of `full-results.json` twice for every person (people × results, roughly a billion comparisons for Victoria). `tabs/improvement.js` now groups one event's results by person once and looks up each person's own results, and Victoria loads in about 2.0 s (cold, measured 2026-10-27):

|---|---|---|
| login module (esm.sh) | 296 | 172 |
| list lookup (RPC) | 616 | 123 |
| files downloaded and parsed | 860 | 566 |
| `renderAll` (every tab) | 523 | 557 |
| remaining renders | **8,479** | **56** |
| total | 12,329 | 1,981 |

### Builds and data
- **Scheduled builds are unreliable** (mitigated by on-demand builds, section 1): GitHub's `*/15` cron ran about every 2 hours when measured (2026-10-19). A new list still waits behind a running daily or weekly run, and normally causes two dispatches (list insert, then member insert); the second finishes fast.
- **Edits show after the next build** (a few minutes). The same goes for opt-outs and state changes: a person who opts out stays in the rankings until then.
- **Parquet / R2:** the R2 copy is refreshed only by the `bests` (daily) and `full` (weekly) runs, and only if the conversion succeeds (`continue-on-error`, so a failure shows as an orange step). A `pending` build therefore reads data up to about a day old (rankings too, since step 7); the 3-day staleness guard forces the fallback (`parse-export.js`, or `fetch.js` for personal bests). `extract-from-parquet.py` reading `s3://` is untested (the workflow uses `https://`). `fetch-upcoming.js` is not on Parquet. GitHub builds still read `r2.dev` (rate limited, uncached); browsers use the Worker first.
- **Instant rankings:** browser-built names ignore the preferred-name rules; the page does not switch to the built data by itself while open; official ranks can be a day behind the built ones.
- **Upcoming:** a new list gets its data about 10 minutes after creation (a `pending` run starts `update-upcoming.yml`; the shared scan takes about 9 minutes). The scan is all-or-nothing: if any competition's WCIF still fails after 8 retries nothing is written, the previous `upcoming.json` stays and the run shows red. Pending registrations are never visible; dormant lists are not scanned.
- **WCA API rate limiting:** the API returns 429 after roughly 60 quick requests. Ordinary builds no longer call it for personal bests; `fetch-upcoming.js` (and `fetch.js` when it runs as the fallback) pace and retry, and fail the step after 8 attempts by design, leaving the data as it was until a later run.
- **State pages are heavy** (VIC about 62 MB of JSON, but about 2 s cold after the 2026-10-27 fix): section 9, "Loading speed".
- A personal profile is a full list build per person (one more list in every full build); fine thanks to the one-pass build, but it adds up.
- The export's real file and column names are only known from the build logs; scripts print the real header and stop if a column is missing.

### Lists and accounts
- **List lifecycle (session 15):** a list only the owner's friends view without logging in, or whose members never log in, can expire (only a logged-in owner or member counts as an open). A dormant list's data can be a month or more old until someone opens it (opening rebuilds it). Expiry can be up to 7 days late because the cleanup runs weekly (the lists page shows "Expires soon" meanwhile). The cleanup step is `continue-on-error`. Opening a list is throttled twice (browser once a day via `fa-list-opens`, server once a day), which matters when testing. Admins never hit the 10-permanent-lists limit.
- Typed WCA IDs are only format-checked (a nonexistent ID builds as an empty person).
- The database rejects `state-` and `me-` slug prefixes for normal lists; other names are not reserved.
- No ownership transfer. Guest limits are partly browser-enforced (a guest who clears browser storage loses edit access). `preferred_name_lists` rows are not removed when someone leaves a list (harmless).
- Unlisted list data in Storage (guest and state lists included) is readable by anyone who knows the list's uuid, which `get_list_by_slug` gives to anyone with the slug.
- FA's old membership and data remain in public git history (accepted).
