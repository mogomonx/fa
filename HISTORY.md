## Loading speed (reported and fixed 2026-10-27; updates to 2026-10-30)

**What happened.** The owner saw Victoria's state page load slowly and inconsistently after publishing. `main.js` now prints two console tables after each load (the load steps, and each file's download / read / parse time), which found the cause: the **Improvement tab's first render took about 8.5 s** of a 12.3 s load. `renderImprovement` scanned all of `full-results.json` twice for every person (people × results, roughly a billion comparisons for Victoria). `tabs/improvement.js` now groups one event's results by person once and looks up each person's own results, and Victoria loads in about 2.0 s (cold, measured 2026-10-27):

| step | before (ms) | after (ms) |
|---|---|---|
| login module (esm.sh) | 296 | 172 |
| list lookup (RPC) | 616 | 123 |
| files downloaded and parsed | 860 | 566 |
| `renderAll` (every tab) | 523 | 557 |
| remaining renders | **8,479** | **56** |
| total | 12,329 | 1,981 |

Files for Victoria (cold): `full-results.json` 28.5 MB and `individual-rankings.json` 23.9 MB download in about 0.5 s and parse in about 35 to 45 ms each, in parallel; the `Storage` response is a 304 on repeat visits. So the earlier plan to stage loading, cache in IndexedDB and trim the state files is **not needed for Victoria**.


**What is left (all small):** (done 2026-10-28, see the update below) `renderAll` drew every tab at load (about 0.55 s on Victoria); the pre-script gap (about 0.45 s before the page script starts); the list lookup RPC. The `esm.sh` module and Storage downloads were not the problem.

**Update 2026-10-28: lazy drawing.** Measured on NSW (the biggest list, about 49 MB) with Chrome's 4x CPU slowdown. Before: `renderAll` took 1,190 and 1,137 ms of about 2.5 s of script time (about 300 ms with no throttling). After: "visible tab drawn" takes 6 ms (the NSW Home tab draws nothing, since state mode skips the members chips) and the five always-live renders take about 157 ms; script time fell to about 1.8 s even though the network steps were slower in that run (files 940 ms against 713 to 761 ms before), so expect about ±200 ms of run-to-run noise. Where the throttled time goes now: the pre-script gap (about 0.7 s, the page's static module graph), the login module (about 0.18 s) and list lookup (about 0.4 s) before any file download starts, and the files (about 0.94 s, of which about 0.8 s is main-thread read and parse: `individual-rankings.json` 246 + 231 ms, `full-results.json` 121 + 65 ms, `rankings.json` 26 + 39 ms, `streaks.json` 13 + 40 ms). Downloads are mostly cached (304) on repeat loads, so the cold-network cost on a phone is still unmeasured: tick "Disable cache" together with Network throttling to measure it. **Ideas, not done:** `<link rel="modulepreload" href="js/auth.js">` in the `index.html` head to overlap the login module with the page's own modules; draw the always-live groups lazily too (about 40 ms on a laptop; they would have to read live data, not the time-travelled `store`); build the event pickers on first open (about 100 ms throttled); smaller or fewer files (the Parquet route is the real fix).

**Update 2026-10-30: Queensland, cold load (owner's console tables, no throttling).** The page script started at 1,969 ms, the login module took 386 ms, the list lookup 142 ms and the files 509 ms (all in parallel; about 32.8 MB in total: `individual-rankings.json` 16.2 MB in 431 ms, `full-results.json` 10.1 MB in 490 ms, `rankings.json` 3.1 MB, `streaks.json` 2.9 MB, `historical-records.json` 0.5 MB; read plus parse stayed under 50 ms per file). The visible tab drew in 0 ms and the live renders took 22 ms, so everything was ready at about 3.0 s. **Reading:** the data is no longer the cost; about two thirds of the time is the 2.0 s before `main.js` starts (HTML, CSS and the static module graph; `index.html` only preloads `auth.js`), which is much larger than the 0.45 to 0.7 s measured on 2026-10-27/28, so it may be a cold-cache effect or a long import chain. To check: DevTools Network, filter JS, look at the waterfall for a chain of files fetched one after another; then try `modulepreload` links for the modules `main.js` imports, or bundling them. Note for the Network tab: opening a file's address in a new tab shows `Bucket not found` because the bucket is private and the page reads it with the login token; that is expected and means the data is not public.
